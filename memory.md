### Decision: `created_at` (F1) — UTC store, IST dikhao, purani rows khaali (2026-10-16)

Lot ledger ka running balance Python loop (id order), SQL window function nahi.

R5 Purchase Return post: lot ki QC_IN row wale warehouse se -qty, pehle on-hand check (`read_return_form` + posting dono, "Only X KG of this lot is still in stock"). R6 return cancel = counter-rows, koi guard nahi. R7 negative stock nahi (4 dp round karke compare). R8 value rule upar. R9 koi UPDATE / DELETE nahi, double click partial unique index se rukta hai. R10 `movement_date` = document ki business date. R12 purane GRNs ke liye backfill (S23) wahi posting functions se.

### Lessons: Docket build + 2 round adversarial verify (2026-10-13)
**Date:** 2026-10-13
**Kya:** Docket user ke "A tum karo" par Claude ne banaya. Pehle user ko docket ka matlab saral shabdon me samjhaya (ek PO ke saare documents ek page par, sirf padhta hai) — user ne bataya tha ki use docket samajh nahi aa raha (Purchase Return tak sab yaad hai). **Naya module shuru karne se pehle pehle simple Hinglish me "ye kya hai, kyun" batao, step IDs / jargon se nahi** (CLAUDE.md rule dobara toota tha).
**Status ke shabd confuse karte hain:** ek hi shabd "Partial" PO, GRN aur QC me alag matlab rakhta tha; user ne screenshot bheja "patti ke 50 pcs aa gaye phir bhi Partial kyun?" (wo QC ka status tha; PO partial isliye tha ki Lead 100 me se 50 hi aaya). Docket me label **quantities se** nikalte hain ("40 of 50 passed", "Partly received: 1 of 2 items fully received. Still to come: Lead 50 KG."), stored status se nahi — stored status lag sakta hai ya galat ho sakta hai. DB ka status nahi badla, sirf dikhane ka naam.
**Asli bug (GRN module):** `refresh_po_status` sab lines ki qty jod deta tha (KG + PCS) aur ek line ka over-receipt doosri line ki kami chhupa deta tha → PO "Closed" aur uski GRN nahi ban paati. Har line alag dekho. Aisa bug tab dikha jab doosre ne docket tod ke dekha — naye feature ka test purane module ke chhupe bug bhi pakadta hai.
**Verification ka tareeka jo kaam aaya:** (1) 4 alag tester agent har ek DB ki copy par (asli DB kabhi nahi) — data audit (independent SQL se har number), robustness / security (XSS, dangling rows, fuzz 8,500 renders, query count), conventions + print (headless Chrome A4 PDF), completeness critic. (2) Fix ke baad **fresh** agents ka dusra round: purane findings ka regression + "non-technical padhne wala" reviewer. (3) Apna regression test (`docket_v3`) jo naye behaviour ke har fix ko pakde. Round 2 ke findings zyadatar "FIXED" nikle aur naye wording / layout ke sudhar aaye. **Seekh:** testers ke 50+ findings me se sab ko mat karo — jo galat data / crash / confusing wording / print toot-na hai wo karo; jo sirf corrupt DB rows se banta hai (UI se nahi) uske liye bas guard / note.
**Chhote technical seekh:** Python ka `%g` 1e+06 / 6 digit par kat deta hai — quantity ke liye apna `format_qty`; lab ke readings ke liye 8 decimal (99.49999 limit 99.5 jaisa na dikhe); rate 2–4 decimal; paisa Indian grouping (5,95,900.00) jaisa baaki pages dikhate hain. Print CSS: heading / block header `break-after: avoid`, har lot ka alag `<tbody>` (`break-inside: avoid`), bade blocks tootne dein, aakhri block + sign lines ek `.endkeep` me, `@page` margin boxes se har page par PO no. + "Page x of y", `opacity` se dim nahi (padhna mushkil) — dashed border + halka grey header. Mixed bill / return me "This PO's lines + Other lines (not shown here) + charges = whole bill total" dikhao taaki numbers jodne par mel khaye. Docket jaisi read-only pages ko `grep commit / add` se saabit karo.

### Decision: Purchase Return — design, charges ka matlab, saral UX aur seekh (2026-10-09)
> ⚠ **2026-10-14: charges ke plain words ("vendor deducts / pays back") SUPERSEDED → sirf Add / Minus; return limit ab Passed / Rejected alag** — dekho "Client feedback round 3" upar.
**Date:** 2026-10-09
**Kya (rules):** Return sirf **Posted bill** ke against, bill ki **line** wise qty. `returnable = bill line qty − active returns ki qty` (Cancelled / is_deleted nahi ginte). **Bill Posted hi rehta hai** aur lot ki `billed_qty` **nahi ghatti** (maal wapas gaya, dobara bill nahi hoga) — return alag document (debit note) hai jo vendor ka payable ghatata hai; ledger `current_balance −= total` (Dr = minus), saari ledger logic `posting.py` (`post_return` / `cancel_return`). Return seedha **Posted** (Draft nahi), baad me Cancel (reverse). **Jis bill par active return ho wo cancel nahi hoga** (server guard `for` + `continue`; template me Cancel button chhupa diya). Return line par sirf `qty` — paisa **bill line ke rate / discount / tax se property** (`taxable_amount`, `tax_amount`): copy isliye nahi ki source line kabhi badalti nahi. Totals server nikalta hai (line-wise round 2), total negative nahi. Return number `PR-year-NNN` (return date ka saal, Cancelled bhi ginte hain — number dobara nahi aata). Return date bill date se pehle nahi. Reason zaroori (free text, master nahi).
**Charges (user ne bola "return me bhi charges lagte he"):** Charges Master se, bill / PO jaisa, charges par GST nahi. **Add / Minus return ke total ke hisaab se:** `total = goods + GST + charges`, payable utna ghatta hai — **Add** = vendor hamara kharcha lauta raha hai (return freight), **Minus** = vendor apni fees kaat raha hai (handling / restocking). DB me `add` / `minus`, par **screen par saade shabd**: "Vendor deducts this from our credit" / "Vendor pays this back to us". Original bill ke charges return me apne aap wapas nahi aate (vendor lautaye to "Add" charge se).
**UX principle (user: "non technical bhi aasani se samjhe warna ghadbad ho sakti he"):** jargon nahi (Dr/Cr, Add/Minus, ledger sign): 3 numbered sawaal (kya wapas? kab-kyun? extra charges?), "You can return" column (limit pehle dikhe, galat qty par "Too much"), summary sirf shabdon me ("Vendor will credit us ₹X", "Bill total after return"), tasalli ki line ("The original bill stays as it is"), Post par plain-English confirm. **Naya screen banane se pehle mockup (visualize) dikhao, tab banao** — user ne mockup dekh ke "thik he" kaha. ### Decision: File upload paths hamesha `/` se banao (store karte waqt), `os.path.join` sirf real disk operations ke liye
**Date:** 2026-10-03
**Kya:** Jab bhi koi uploaded file ka **relative path DB mein store** karna ho (taaki baad mein `send_from_directory` se wapas serve ho sake), us path ko seedha `/` se jodo (jaise `'purchase_orders/' + str(po_id) + '/' + safe_name`) — `os.path.join()` **mat** use karo us jagah. `os.path.join()` sirf tabhi use karo jab seedha disk pe real file read/write/save ho raha ho (jaise `folder = os.path.join(UPLOAD_FOLDER, ...)` aur `invoice_file.save(...)`).
**Kyun:** `os.path.join` current OS ke hisaab se separator choose karta hai — Windows pe `\`, Linux pe `/`. Lekin Flask ka `send_from_directory` (aur uske andar `safe_join`) hamesha forward-slash (`/`) rules se path-safety check karta hai, OS chahe jo ho — URL/web-path jaisa, filesystem-path jaisa nahi. Isliye Windows pe save hua backslash-wala path (`purchase_orders\4\test.pdf`) `send_from_directory` ko ek hi ajeeb-naam wali file dhoondne pe majboor karta hai, jo exist nahi karti — 404. User ne khud poocha "Linux VPS pe deploy karne se yeh theek ho jayega?" — jawab: naya data Linux pe sahi banega (kyunki wahan `os.path.join` khud `/` use karta hai), **lekin Windows pe pehle se likha hua backslash data DB ke andar hamesha kharab rahega**, chahe DB file Linux server pe copy kar do — isliye root fix zaroori hai, "bas Linux pe deploy kar denge" kaafi nahi.
**How to apply:** §10.5 (PO invoice upload) mein pehli baar mila, fix kiya (`app/purchase_orders/routes.py`). **Agle file-upload features** (§10.4 Vendor/Customer document upload, §10.8 Unified Procurement Docket) banate waqt yehi pattern shuru se follow karo — stored path hamesha `/`-joined string, kabhi `os.path.join` ka result seedha DB mein mat daalo.

### Decision: Table columns — fixed px width for content, ek column flexible (px-based colgroup technique)
**Date:** 2026-09-15
**Kya:** Data tables me `%`-based colgroup widths use nahi karni — bade/wide screen par short-text columns (jaise "Full name": "Kilogram", "Gram") % width ke hisaab se zabardasti stretch ho jaate hain aur beech me bada khaali gap dikhta hai. Sahi tarika: `table-layout: fixed` rakho, per-column **fixed px width** do (content ke hisaab se, jaise # =44px, Code=92px), aur flexible column (usually "Actions", jahan trailing space normal dikhta hai) ko **explicit `width: calc(100% - <baaki columns ka total px>)`** do.
**Correction 1 (same day):** Pehle socha tha ki flexible column ka `<col>` bas width-less chhod dene se (koi width attribute hi nahi) wo khud bachi hui jagah le lega — practically yeh reliably kaam nahi kiya (Actions column chhota reh gaya, page ka right side pura blank dikha). `calc(100% - Npx)` explicit value dene se yeh guaranteed kaam karta hai.
**Correction 2 / Final decision (same day):** `calc()` se Actions column ko poora leftover space diya to Actions hi bahut chauda (30%+) ho gaya aur wahi "ek jagah bada khaali block" problem repeat ho gayi, bas column badal gaya. User ko 2 options diye (AskUserQuestion se): (a) table ko compact/content-width rakho, ya (b) poori width cover karo lekin gap har column me evenly spread karo. **User ne (b) chuna.** Final approach: colgroup % based hai (#5%, Code9%, Full name22%, Base unit14%, Status20%, Actions30%), aur **saare columns (headers + data cells) center-aligned** hain (`text-align:center` — sirf # column left rehta hai) + Actions ke andar Edit/Toggle bhi `justify-center` se center kiye. Isse extra space kisi ek jagah "khaali block" nahi lagta, balki har cell me evenly padding jaisa spread hota hai.
**How to apply (updated):** Future modules me bhi is "poori width + center-align sab kuch" pattern ko default maano jab tak user kuch aur na kahe — sirf ek column ko flex/calc dena (jaisa pehle try kiya) is user ke liye kaam nahi karta.
**Kyun:** Pehle attempt me maine page/`<main>` ka hi max-width chhota kar diya tha (1680→1120px) taaki columns ke gaps chhote dikhein — lekin isse page ke SIDE me khaali jagah dikhne lagi, jo user ko bilkul pasand nahi aaya ("pehle sahi tha"). Asli problem page-level nahi, table-level tha — column sizing ka tareeka galat tha.
**Result:** `<main>` ka max-width cap poora hata diya (page phir se full-width hai). Table ke colgroup ko %  se px me convert kiya, sirf Actions column flexible chhoda. `mockups/unit_master.html`.
**How to apply:** Future modules (Machine, Vendor, Customer, Raw Material, Product tables) me bhi yehi pattern follow karo — pehle content dekh ke har column ka natural px width tay karo, phir sirf ek "safe" trailing column (aksar Actions) ko flexible rakho. Kabhi bhi poori page ko chhota mat karo sirf table ke andar ke gaps fix karne ke liye — yeh do alag problems hain.
